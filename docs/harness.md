# TRACE harness

The active [detection product roadmap](../TODO.md) tracks remaining detector implementation, calibration, product integration and testing. Its tasks are planned work; the runtime behavior and qualification limits below describe the current implementation.

`packages/harness` contains the MMD scorer, calibration, account state, and graduated policies. `apps/harness-api` exposes the protected teacher endpoint. `harness calibrate --help` and `harness replay --help` describe their inputs. The gateway adds a domain tag to each user turn before detector serialization. For gateway calibration, use `distill gateway detector-input` and `--task gateway` so calibration and serving apply the same domain-specific serialization.

A new account starts at L0. L1 is an alert that still serves; L2 adds spacing; L3 adds proof of work; L4 refuses when configured with `HARNESS_L4_ACTION=refuse`. Quota and rate policies are alternative controls. A detector window is not completed until enough requests arrive, and a completed window's decision can affect the triggering request. Account identity, horizon resets, caps, and policy settings affect results. Inspect the source and calibration metadata for exact settings.

The protected API logs admission and release separately. A `decision` event records each admitted attempt. Before producing any output, the service reserves that admission in a release ledger. A `release` event then records exactly one settlement: `released` (output made available, with the server's output-token count), `failed` (upstream error) or `cancelled` (the client left before anything was emitted). An admission releases at most once, and failed or cancelled attempts still count against the account. Without `HARNESS_STATE_DB`, account horizons, open challenges and the ledger live in process memory, so a restart renews every account. With it, they are kept in a SQLite file that survives restarts. A reservation left unsettled by a crash counts as acquired. A state file belongs to one policy configuration and calibration, and opening it under another is rejected, so use a new file for each arm. The aggregate monitor still lives in memory, so run one worker.

`HARNESS_POLICY_VERSION=verify-risk-v2` opts the MMD policy into recoverable treatment of detector risk. L1 serves, L2 spaces, and L3 and L4 require a proof for each response. This version neither labels detector evidence confirmed abuse nor applies L4 deception. A successful proof releases only the bound request; it does not reduce the level or renew the attempt budget. The separate attempt cap still refuses requests until the horizon expires. Proofs expire at `HARNESS_CHALLENGE_TTL_SECONDS`, bind to the account and canonical request, and can be redeemed once. A proof is rejected if the horizon expired, the cap was exceeded, or the account reached a stronger level after issue. A rejected proof requires a new admission and challenge, subject to the same attempt cap. Optional human review is described below. With `HARNESS_STATE_DB`, these checks run in the same durable transaction that consumes the proof. The default `legacy-v1` preserves frozen behavior.

Calibration uses distinct fitting, score-calibration, and policy-calibration data. Keep a further source-disjoint benign test set and fixed attacker schedules. Synthetic users, shared sources, small account samples, and incomplete windows limit what the resulting rates say about real traffic. A content-based detector may not distinguish an attacker whose request distribution resembles legitimate traffic.

New calibration artifacts record each level's target, threshold, scored and censored horizons, detector reaches, quota-capped horizons, combined reaches, achieved rate, and one-sided 95% binomial upper bound. Thresholds are fitted on scored policy-calibration horizons, not the held-out test set. Censored horizons lack a complete detector window; they are not evidence of a successful detection or non-detection. The adequacy report can select levels and states the sample resolution for each. Its minimum counts only establish whether the target is resolvable, not that the upper bound meets the target or that dependent horizons support population error control. Legacy artifacts without level results load with their historical behavior and report `legacy-inferred` evidence.

Calibration can record a `mixture_control` that scores shuffled, pooled benign windows against the per-account null. It warns when at least 90% rank below the median account window. The warning identifies a possible blind spot for broad traffic and does not change the adequacy verdict. Older calibrations may not include this control.

Pass `--mixture-control-required` to `harness calibrate` to record an opt-in adequacy gate in the calibration configuration. For selected accumulator defenses, adequacy then fails when the control is missing, has no windows, or reaches the 90% warning threshold. The default remains warning-only, including for older calibration artifacts. This gate does not establish detection effectiveness.

`distill gateway collect` runs a separate detectability gate before an MMD campaign. It calls `harness.replay.replay` on the frozen attacker schedule and on held-out benign accounts, and refuses the campaign when no declared MMD arm escalates the attacker beyond them. `--allow-undetected` overrides it, and the override is recorded as a quota comparison. Gate embeddings are cached in a content-addressed directory keyed by encoder identity and exact detector text. Keep that directory outside calibration artifacts. See [evaluation](evaluation.md#execute-and-report).

The [offline MMD audit](../readings/v4/README.md) reproduced the frozen v3 calibration and logged window scores. Its v2 A1 and A7 ledgers are retained with the audit as evidence for token analysis. In that study, the full policy released all 6,000 A1 responses; broad traffic scored closer to the pooled reference than many specialist benign accounts. Alternative tail tests were exploratory and require independent validation. The audit also identified category bias in the synthetic calibration workload. Correcting it requires fresh workloads and calibration; historical results do not establish current deployment behavior.

The opt-in `gateway-clients-v5` workload uses the five source-family roles described in [evaluation](evaluation.md). `harness calibrate` requires a passing `--validation-report` whose detector-input hashes match the reference-fit, score-calibration, and policy-development files. `--allow-invalid-workload` permits a diagnostic calibration when validation is missing or fails; the artifact records the override and its adequacy verdict fails. The legacy input format remains valid without a report. The optional `--mixture-control-required` gate is independent of source validation. These checks do not establish population false-positive control.

## Shadow scorers

The shadow scorers are telemetry only. They never set a level, an action, a response, or a budget, and they have no thresholds. Raw request and token accounting is unchanged. They address two findings of the [audit](../readings/v4/analysis/REPORT.md): the pooled upper-tail MMD ranks broad extraction as ordinary, and topic-sorting the same prompts evades every fixed-window variant.

- **Domain-conditional MMD.** Each gateway domain has its own references, drawn from fitting requests in that domain, and its own null. The null is built from per-account windows of single-domain score-calibration horizons, which are the specialists. An account's requests in one domain form that domain's windows. The p-value is the upper-tail rank in that domain's null. A domain abstains, logging a null p-value with a reason, when its null has fewer than `ceil(1 / target) - 1` non-overlapping windows. Overlapping windows add resolution but do not count toward that minimum.
- **Cumulative coverage.** Cells come from seeded k-means on the fitting embeddings. A horizon's coverage is the set of cells its distinct prompts occupy, so no reordering of the same prompts can change it, and repeats count once. Coverage grows with volume, so the rank uses rarefied coverage instead: the exact expected number of cells occupied by a uniform random subset of a checkpoint size. It is ranked against score-calibration horizons of each profile at the largest checkpoint the horizon reaches whose null resolves the target. Profiles are `all`, plus `single_domain` and `multi_domain` for the gateway, inferred from the domains a horizon has used so far. Each rank reports its null size, or an abstention reason. `cells_p_value` ranks the raw cell count, which mixes breadth with volume.

Calibrate with `harness calibrate --shadow`. `--shadow-target` defaults to 0.05 and `--shadow-cells` to 128. Fitting supplies the references, bandwidths and cells. Score calibration supplies both nulls. Policy calibration is not used. The settings are recorded in the artifact's `shadow` field, with arrays in `shadow.npz` hashed in `sha256`. Without `--shadow`, the artifact is unchanged. Artifacts without the field load as before and serialize byte-identically, so policy revisions and state-file scopes are not affected. `--embeddings` reads a cached npz of `keys` (SHA-256 of the detector text) and `vectors` in place of the BGE model.

In the API, `HARNESS_SHADOW_SCORERS=true` adds a `shadow` object to every `decision` event that reached the policy: coverage after the request and, when the request completes a domain window, that window's conditional score. Requests refused early for a spent rolling budget are not observed. Shadow state is per account horizon and lives in process memory, so a restart resets it. The setting is not part of the policy revision. A shadow failure logs `shadow_error` and the request continues. Shadow work runs on the request path in every arm, including `off_path` mode. Each request updates coverage, and each completed domain window is scored inline after the admission commits. A non-embedding policy also loads the encoder and encodes each request before admission. Enabling the scorers therefore changes latency. Do not enable them in arms whose timing is being compared. The added cost has not been measured.

`harness shadow-check --calibration DIR --requests FILE [--reorder topic]` replays BenignRequest or gateway schedule lines through the shadow scorers only. It reports coverage and per-domain window summaries for each account horizon. `--reorder topic` sends each horizon grouped by domain, then by coverage cell, while keeping the original times.

**What this does not establish.** Neither score identifies extraction or intent. Coverage measures breadth, which benign generalists and broad researchers share, and splitting a campaign across accounts removes it. Conditional MMD can only flag traffic unlike a domain's specialists, such as foreign-source prompts. When an attacker's prompts follow the same distribution as benign traffic, every content-only score, these included, rejects attacker and benign accounts at the same rate. No false-positive rate, detection rate, or effect on student capability has been measured. Any use in a policy needs a fresh source-disjoint calibration and evaluation.

## Acquisition accounting

By default the service keeps enforcement state in memory and enables no new entitlement limits. Set `HARNESS_STATE_DB` to a persistent SQLite file shared by all workers to retain account horizons, challenges, reservations, idempotency records, and partial aggregate windows across restarts. SQLite serializes writes; use a separate file for each policy, calibration, reference set, account mapping, tokenizer, or accounting configuration. Opening an incompatible file fails. The aggregate stream, window index, and scored alerts are shared and persisted transactionally in the state database. The JSON-lines decision log is separate: a crash after the database commit can omit its corresponding aggregate event; the committed alert remains in the `aggregate_alerts` table. The deception response template and latency sample remain process-local.

`HARNESS_OUTPUT_TOKEN_BUDGET` sets a positive per-principal output-token allowance per calibration horizon; `HARNESS_ORGANIZATION_TOKEN_BUDGET` sets an optional shared allowance. The accounts JSON may map a key digest either to the existing principal string or to `{"principal": "alice", "organization": "example"}`. A principal must have a consistent organization, and the organization limit rejects principals without one. Organizations are explicit; no links are inferred. Both allowances are checked and reserved together with the admission, before inference, using the requested maximum output tokens. A challenge reserves at issuance, so an unanswered challenge retains its token charge; proof redemption uses the same reservation and key. Successful output is charged at the configured tokenizer recount, or the teacher's reported output count if no tokenizer is configured. Failed and cancelled requests retain the full reservation. When an entitlement is enabled, unknown counts or a count above the reserved maximum cause the response to be withheld. The bound depends on an accurate tokenizer or teacher report and on traffic passing through this service; it is not a claim about unobserved or misreported tokens.

`HARNESS_IN_FLIGHT_LIMIT` optionally caps outstanding generations per principal. `HARNESS_RESERVATION_LEASE_SECONDS` sets their lease, default 600 seconds. A crashed reservation holds its slot until expiry and keeps its full token charge; an expired worker cannot settle a successful response and must withhold it. Outstanding reservations remain charged across horizon rollover. Choose a lease long enough for the configured teacher timeout and any policy delay. Test-clock mode uses the supplied time and is only for tests.

Clients may send `Idempotency-Key`. A key is scoped to the principal and bound to the canonical request and detector turn; reuse with different content returns 409. Completed outcomes, including challenges and rejections, are returned on retry without another generation. A challenge may be redeemed with the same key. Concurrent retries or a crash before the outcome is stored return 409 pending; they never start another generation. Pending keys are retained indefinitely and need operational reconciliation rather than automatic reuse. The database contains stored response bodies and must be protected as sensitive data. A response is recorded as released before it is returned, so a crash after commit can be retried from the stored response. API responses are buffered, not streamed.

## Named request-plus-token quota

`HARNESS_POLICY=quota_tokens` composes the existing request quota with transactional output-token reservations; it does not add another counter. Set `HARNESS_STATE_DB` and a positive `HARNESS_OUTPUT_TOKEN_BUDGET`. Startup rejects this named arm without both. Reservations and settlement keep the existing conservative rules for crashes, failed/cancelled requests, unknown usage and outstanding work across horizons. Request-quota refusals return 403 and token-entitlement refusals return 429 through the existing endpoint behavior.

For either quota or quota_tokens, `HARNESS_REQUEST_QUOTA=N` selects a measured development grid point; omitting it uses the calibration's request quota. The override enters the state scope only when set and requires a fresh state file. Other policies reject it. Declare the arm with `distill gateway collect --policy quota_tokens` against an already-configured server. The collector checks the reported policy and does not configure the endpoint. Query-only replay cannot enforce output reservations. Keep other budgets and review settings equal across comparison arms. [Quota matching](evaluation.md#utility-validity-and-measured-quota-matching) selects measured settings but does not execute the experiment or prove protection.

## Encoder batching

The default `HARNESS_ENCODER_BATCH_WAIT_MS=0` preserves per-request encoding. A positive value enables a bounded FIFO microbatch queue. Set `HARNESS_ENCODER_DEVICE=cuda` on a host with a verified CUDA device, `HARNESS_ENCODER_BATCH_SIZE` to the maximum batch size, and `HARNESS_ENCODER_QUEUE_CAPACITY` to the maximum number waiting. A full queue returns HTTP 503 before policy admission; encoder failures also return 503. Shutdown drains accepted batches. Cancellation removes a waiting request from its batch where possible. The model, revision, pooling, normalization and truncation contract remain unchanged. Batching can change request completion order and timing, so remeasure the deployed workload. A CPU setting or automatic CPU fallback is not GPU qualification.

## Off-path scoring

`HARNESS_SCORING_MODE=synchronous` keeps the frozen policy: the triggering request waits for its window score. The experimental `off_path` mode submits completed windows to a single FIFO worker with `HARNESS_SCORING_QUEUE_CAPACITY` waiting slots. The triggering request uses the current level, and a later request can be served before the score takes effect. Scores are applied in sequence and only to the account horizon that generated them. A full queue or scorer error returns HTTP 503 and disables further admission until restart. Shutdown drains accepted work. This mode requires its own calibration and qualification, including delay and overshoot; the synchronous calibration and historical results do not qualify it. The repository does not yet provide an off-path calibration or a durable multi-process account store.

`off_path_score` records the horizon start, window sequence, closure and application times, delay, admissions after closure, server-side releases and known output tokens before application, unknown-token response count, and in-flight work at closure and application. A null `total_released_tokens` means at least one released response had unknown usage. Counts refer to successful ASGI response-body handoff, not proof of receipt by a remote client. Reservations are null; these records are not yet reconciled with the reservation ledger. Queued windows live in process memory, so `off_path` refuses to start with `HARNESS_STATE_DB`. Score errors are logged with the partial counters; do not treat those windows as qualified. Challenge redemptions are counted only when they actually release a response. A stale score is logged with `applied=false` and cannot change a new horizon.

A release can fall inside several overlapping score-delay intervals. Each window record counts it once for that interval, so summing records across windows double-counts shared releases. Reconcile event identities with the durable accounting implementation before reporting a campaign-wide total.

## Rolling budgets

`HARNESS_OUTPUT_TOKEN_BUDGET` renews with the calibration horizon, so an account that spends it can spend it again the next day. `HARNESS_ROLLING_REQUEST_BUDGET` and `HARNESS_ROLLING_TOKEN_BUDGET` instead limit what one principal can acquire in any span of `HARNESS_ROLLING_WINDOW_SECONDS`, seven days by default. They read the same ledger charges as the horizon budget and are checked in the admission transaction. Requests and tokens leave the budget one at a time as they age out of the window. Use them with `HARNESS_STATE_DB`: without it a restart empties the ledger and refills them. They do not count noise, which releases no teacher output.

`HARNESS_ORGANIZATION_ROLLING_REQUEST_BUDGET` and `HARNESS_ORGANIZATION_ROLLING_TOKEN_BUDGET` set the same limits for everything the principals of one declared organization acquire together, over the same `HARNESS_ROLLING_WINDOW_SECONDS`. The organization comes from the accounts JSON, as for `HARNESS_ORGANIZATION_TOKEN_BUDGET`. Each charge counts against the organization its principal was mapped to when it was admitted. They read the same ledger charges and are checked in the same admission transaction as the per-principal limits. With either set, a principal without an organization is refused with `organization_required`, as the horizon organization budget does. Both scopes can be set together. When both are spent, the refusal names the per-principal limit.

A principal with a spent rolling budget is refused with `rolling_budget_exceeded` before any embedding, so that refusal logs a decision with `attempt` null and does not count as an attempt. A principal whose organization's rolling budget is spent is refused the same way with `organization_rolling_budget_exceeded`. This differs from the horizon budget and from `organization_required`, whose refusals count. A request that passes this check can still be refused at admission if another one spends the budget first, which is more likely when several principals share an organization's budget. Setting a rolling limit, either per principal or per organization, changes the state scope, so use a new file; leaving them unset keeps existing files valid.

Decision events record a `reason`: `attempt_cap`, `quota`, `rate`, `detector`, or null. Entitlement refusals are in `entitlement`. Decision and release events also record `policy_revision`, a hash of the policy settings and calibration.

## What budgets establish

Budgets are access controls, not a detector. They limit what one account, or the accounts declared under one organization, can receive. They do not identify an attacker, and they do not change the upper-tail MMD miss described above.

The bound depends on an accurate token count, traffic passing through this service, and an intact state file. Limits apply per principal, or per declared organization for the horizon and rolling organization budgets. An organization limit covers only principals the operator has mapped to that organization. The harness does not infer links between accounts, and it does not apply a ban or a limit across accounts the mapping does not join. A Sybil campaign such as A5 or A6, or account rotation, whose accounts are not mapped together gets one allowance per account, or per organization when the accounts sit in several declared organizations.

**Not measured.** No rolling budget has been run with the real teacher, the encoder, or the MMD policy. No organization rolling budget has been run against any recorded campaign; its tests check enforcement with a stand-in teacher. Student capability under any budget, real legitimate traffic, adaptive attackers, account rotation, and how often real Sybil accounts would be declared under one organization are all unknown.

**What this supports.** "With the stated assumptions, the harness bounds the requests and output tokens released to one principal, and to the principals declared under one organization, in a rolling window."

**What this does not support.** Do not claim that budgets prevent distillation, reduce a student's capability by a stated amount, improve detection, or leave legitimate users unaffected, or that any limit value is safe. A smaller release is not a proportional loss of capability: the audit's development AG News gain came from 500 responses, so a campaign held below 1,215 may still train a useful student. A budget also says nothing about an attacker with more accounts, other data sources, or another provider. An organization budget does not establish that a Sybil campaign is contained: that depends on the operator declaring its accounts together, which the harness does not do. Learning curves on fresh sources and a protected run are required before any effectiveness claim.

### Weighted and tiered rolling allowances

Set `HARNESS_ROLLING_SUPERVISION_BUDGET` and `HARNESS_SUPERVISION_WEIGHTS_FILE` together to enable supervision accounting. The UTF-8 JSON file has the form `{"version": 1, "weights": {"text": 1.0}}`; include a positive finite weight for the served task, or for every configured gateway domain. Its SHA-256 enters the policy revision and state scope. Charges use the domain weight times the actual output tokens after release and the reserved maximum otherwise. `HARNESS_SUPERVISION_REPEAT_FACTOR` defaults to 1 and may be set between 0 and 1 to discount an exact canonical request whose earlier response was released in the same principal's rolling window. Noise does not count. Failed, cancelled, and outstanding reservations keep their full token reservation. The raw rolling request and token budgets remain independent hard limits. Supervision weights are an accounting choice, not a measured information quantity. Choose and evaluate them against learning curves in `packages/distillation` (`learning_curve*`), rather than treating the weights as evidence of student capability.

Set `HARNESS_TRUST_TIERS=true` to use tiers in the accounts JSON. Object entries may include `"tier": "new"`, `"established"`, or `"verified"`; omitted tiers are new. New principals receive `HARNESS_NEW_TIER_FRACTION` of their principal rolling request, token, and supervision budgets, default 0.5. Integer limits are rounded down. They are promoted when their first ledger reservation is at least `HARNESS_NEW_TIER_MIN_AGE_SECONDS` old and they have at least `HARNESS_NEW_TIER_MIN_RELEASES` clean releases across the ledger. A clean release is non-noise and was admitted at policy level zero. The defaults are seven days and ten releases. Promotion uses durable history when `HARNESS_STATE_DB` is set; without it, restart loses history. Detector evidence never automatically demotes an account. Configure tiers and thresholds to match the deployment's trust process.

A verified principal's organization may declare `"contractual_rolling_budget": {"requests": 1000, "tokens": 500000}` in its accounts entry. Either limit may be omitted. This explicit organization-wide contract replaces the global organization rolling limits for that organization; all declarations for the same organization must agree. Principals and organizations remain explicitly mapped. A spent weighted or tier limit returns `supervision_budget_exceeded` or `tier_budget_exceeded` before embedding with a null attempt. New policy settings require a new state file. These controls have not been evaluated for student capability or legitimate-user cost.

### Human review

Set `HARNESS_REVIEW_ENABLED=true` and `HARNESS_STATE_DB` to record refusals and challenges as appeals. Client details include a limit code, scope, reset time when known, and appeal reference. Operator decisions are append-only. `harness review list`, `harness review show REF`, and `harness review decide REF --action ACTION --operator NAME --reason TEXT` use `HARNESS_STATE_DB` or `--state-db`. Actions are `grant`, `restore`, `unlink`, and `reject`. Grant and restore require `--requests` and/or `--tokens` and `--expires-at` as a Unix timestamp; credits apply to the budget window identified by the appeal. A grant on a policy refusal allows the stated number of requests and/or tokens for that refusal code until expiry, subject to the other admission budgets. A later decision on the same appeal supersedes the earlier decision. Unlink applies only to future admissions and leaves old reservations intact.

Set a separate `HARNESS_REVIEW_ADMIN_KEY` to enable `/admin/reviews` and `/admin/reviews/{ref}` and POST `/admin/reviews/{ref}/decisions`. Send the key in `X-Harness-Admin-Key`. `HARNESS_REVIEW_VERIFY_CODES` is a JSON list of refusal codes that should return a pending verification response instead of a hard refusal. Review is off by default and does not change the policy revision.

### Opt-in offline detection evidence

The request path still uses only the existing policy and volume budgets. `harness evidence-calibrate` and `harness evidence-check` are offline sibling commands to `shadow-check`; they never produce decisions, responses, actions, entitlement changes or transitive bans. They store new nulls separately in an `evidence-v1` JSON file. Existing calibration serialization, policy revisions and state-file scopes are unchanged. `HARNESS_SHADOW_SCORERS` continues to control only the existing request-path shadow monitor.

Generate fresh references with `distill gateway session-benign --output artifacts/session-score --role score_calibration`. Defaults request 20 source-group-disjoint coding specialist account windows, 20 GSM8K windows, and 150 multi-domain generalist account horizons, each with 100 requests. The generator fails if a role pool cannot supply them; it never clones accounts to meet a count. Source groups cannot cross account boundaries. Generate fitting and policy-calibration roles separately and retain source-disjoint task pools. Run the existing `harness calibrate --shadow` with the fresh role files before fitting the new evidence nulls. The manifest records session parameters, realized event counts, provenance and hashes. Sessions include explicit follow-ups, wrapper rephrasing, retries, category drift, lognormal gaps and pauses. These are synthetic sessions: their nulls bound behavior claims to this generator, and do not establish real-user false-positive rates. Follow-up and rephrasing wrappers are offline calibration inputs and can violate the live gateway's fixed task templates; they are not a live utility workload.

```bash
distill gateway detector-input --input-dir artifacts/session-score --output artifacts/session-score-detector.jsonl
harness evidence-calibrate --calibration artifacts/fresh-calibration --score-calibration artifacts/session-score-detector.jsonl --embeddings artifacts/cache.npz --output artifacts/evidence.json
harness evidence-check --calibration artifacts/fresh-calibration --evidence artifacts/evidence.json --requests readings/v3/schedules/A1/s42-b6000/requests.jsonl --embeddings artifacts/cache.npz --output artifacts/evidence-A1.json
```

The calibration command verifies the input matches the existing calibration's declared `score_calibration` role. The evidence artifact binds the calibration file and encoder identity; a different embedding cache requires a fresh evidence artifact. Both commands support an explicitly registered `--corpus-index`. New outputs refuse to overwrite an existing file. `evidence-check` accepts the same BenignRequest or gateway schedule formats as `shadow-check`, including schedules exported from A8 collection. It can run without a teacher. `--reorder topic` changes account prompt order while keeping arrival-time slots. It reports existing conditional MMD and coverage when the base calibration has shadow arrays.

Upper-tail ranks require at least 19 independent horizons at target 0.05; conservative two-sided session ranks require 39. Each score reports its null count, resolution floor and abstention. Missing timestamps/statistics and missing corpus data abstain. Profile selection is fixed to single-domain versus multi-domain account traffic, with `all` outside gateway tasks; no favorable-null search occurs. Short and long horizons are currently pooled within each profile, so exchangeability across account length remains a validity assumption.

Register operator-owned pinned public prompts with `harness corpus-index --sources sources.json --output artifacts/public-corpus.json`, where `sources.json` maps provenance labels to prompt-string lists. Labels should include dataset revision, split and any local manifest hash. Include the independently pinned A3/A7 external pools declared in `packages/distillation/src/distillation/external_sources.py`; index registration does not download corpora or imply a license grant. Store the index outside calibration directories. Its digest covers content, labels, matching settings and version; evidence scoring rejects a changed or missing calibrated index.

For clustering, pass `--links links.json` to `evidence-check`. The document accepts `organizations` mapping principal to organization, `edges` containing `left`, `right`, `source`, `strength` and optional `inferred`, optional `created_at` timestamps, `benign_truth` group labels, `infer` and `minimum_strength` defaulting to 0.8. Optional inferred edges disclose creation proximity, timing correlation and shared-template heuristics. Strengths are declared or heuristic, not identity probabilities. Connected components are an analysis hypothesis only. Reports retain all edge evidence and inclusion decisions, cluster complementarity, and pairwise false merge/split counts, denominators and rates when benign truth exists; absent truth yields unknown rates. Pooled cluster reports use the supplied analysis interval rather than automatically splitting it into policy horizons. No request-path graph is created.

Fusion uses a frozen five-family mixture with weight 0.2 each: volume request count, session revisit/follow-up rank, novelty rank, linkage and corpus-match content rank. Linkage remains neutral until a separate fixed cluster null exists. Missing families contribute e=1 without reallocating weights. Valid horizon p-values become e-values by `0.5 / sqrt(p)`, then receive a convex average, never a max or a product across correlated sensors. Validity requires superuniform family ranks under exchangeable same-profile benign horizons and fixed missingness by design/profile, or calibration of the full missingness rule. Arbitrary dependence among valid families is allowed. These assumptions are not certified by empirical ranks, synthetic data, adaptive graph selection or volume-dependent missingness. The result is shadow evidence, not a sequential e-process or a time-uniform guarantee. Freeze components, weights, missingness and thresholds on development data, then test once on locked data.

## Experimental coverage and whole-campaign stopping

`harness.logdet` adds an opt-in geometric coverage proxy. It normalizes embeddings, applies a frozen seeded 64-dimensional random projection, and computes each prompt's incremental log-determinant gain with a Sherman-Morrison update. The mean gain after the first prompt is ranked against same-profile reference horizons in the same request-count band. This is a geometric novelty measure, not information about teacher weights or a predictor of student learning. Cumulative log-determinant is deliberately excluded because it grows with volume.

Enable fitting through `harness evidence-calibrate --coverage-seed SEED --coverage-width WIDTH --coverage-ridge RIDGE`; WIDTH must be the actual encoder/cache embedding width. The evidence artifact records the projection digest and fitting provenance. `harness evidence-check` reports coverage and nearest-neighbor novelty on the same input horizons, including abstentions. It rejects reused fitting accounts or exact fitting prompts; source-family and temporal independence still require an audit. These comparisons have fixture coverage, not measured superiority on real held-out clients.

`harness.path_calibration` calibrates the maximum frozen score over each benign campaign's complete permitted path. For a runtime running maximum m, it uses `(1 + count(benign campaign maximum >= m)) / (n + 1)`. It stops at the first conservative rank at or below alpha. Under exchangeability of complete benign campaigns with the same recipe, stratum and horizon, this controls any statistical stop within that finite horizon. It does not establish validity under drift, adaptively selected groups or unmodeled intermediate interventions. The artifact binds all streams, positive weights, feature settings, detector/encoder identities, look schedule, horizon and calibration maxima; hashes establish consistency, not benign provenance.

Declare H before calibration as a positive multiple of the detector window size. Each authenticated principal's rows in file order form one calibration campaign, with at least one complete look and no partial final look. Shorter paths must represent genuinely ended campaigns, not favorable truncations selected after scoring. Fit representation/feature nulls, select methods, calibrate paths and audit on separate independent accounts/source groups. Fewer than 99 campaigns cannot resolve alpha 0.01; fewer than 999 cannot resolve 0.001. Sparse strata abstain rather than borrowing another population's null.

For a gateway calibration with 100-request windows, an example MMD-only artifact is:

```sh
devenv shell -- uv run harness path-calibrate \
	--calibration artifacts/fresh-calibration --campaigns benign-paths.jsonl \
	--output artifacts/path.json --request-horizon 200 \
	--stratum multi_domain --alpha 0.01 --streams mmd --weights 1
```

Optionally declare stream coverage_mean_logdet with an independently fitted coverage evidence file and matching weights. The runtime scores the existing raw MMD window and the coverage mean's negative log upper-tail rank at predetermined nonoverlapping window boundaries. Every declared stream must be available; missing coverage bands abstain rather than silently changing the score. No cumulative log-det or count stream is allowed. Adding another session model requires a new scorer version and fresh path calibration; the existing horizon-fusion output is not automatically a valid path score.

Select the experimental arm with `HARNESS_POLICY=path`, `HARNESS_PATH_CALIBRATION=artifacts/path.json`, `HARNESS_STATE_DB=artifacts/path.sqlite3` and synchronous scoring. Missing durable state and off_path scoring are rejected. The arm serves until a terminal path_stop, without intermediate detector challenges, delays or deception. Existing attempt and release entitlements still apply. The optional path fields and state scope leave the default policies unchanged when this arm is not selected. Use a fresh state file for a changed recipe.

The campaign is one principal's first H evaluated prompt admissions. Authentication and early rolling-budget rejections do not enter the path; idempotent retries do not advance it. A stopped principal stays stopped across restarts, contexts and renewable account horizons, and review credits cannot bypass that stop. At H without a stop, statistical scoring expires and abstains while ordinary limits continue. There is no automatic rearming, lifetime alpha allocation or Sybil resistance. Changing authenticated principal creates another campaign. Gateway single_domain or multi_domain strata must be fixed before calibration; leaving the supported stratum permanently disables subsequent statistical stops and cannot erase an existing stop. Multi-domain traffic must reach that stratum by its first look.

Feature preparation runs outside the database write lock and admission commits only against the same campaign revision, retrying stale preparation. The evaluated prefix follows committed admission order. Incoming requests are decided before teacher dispatch; previously admitted in-flight outputs may still be released after a stop. Decisions and releases identify path_stop separately from quotas, attempt caps and failures and carry qualified: false. No zero-overshoot or extraction-prevention claim follows from this implementation.

The current path state retains all prefix embeddings and serializes them with admissions, and coverage recomputes over the prefix. Memory, storage and latency therefore grow with H. Keep this as a short-horizon experimental arm and profile it on the target host; large campaign budgets require compact incremental state and bounded cost before deployment. It has no independent benign audit or teacher/student effectiveness measurement. The standalone period_alpha and audit_upper_bound helpers do not implement operational period renewal; the latter uses a separate stable calculation and leaves legacy calibration values unchanged.
