# TRACE harness

`packages/harness` contains the MMD scorer, calibration, account state, and graduated policies. `apps/harness-api` exposes the protected teacher endpoint. `harness calibrate --help` and `harness replay --help` describe their inputs. The gateway adds a domain tag to each user turn before detector serialization. For gateway calibration, use `distill gateway detector-input` and `--task gateway` so calibration and serving apply the same domain-specific serialization.

A new account starts at L0. L1 is an alert that still serves; L2 adds spacing; L3 adds proof of work; L4 refuses when configured with `HARNESS_L4_ACTION=refuse`. Quota and rate policies are alternative controls. A detector window is not completed until enough requests arrive, and a completed window's decision can affect the triggering request. Account identity, horizon resets, caps, and policy settings affect results. Inspect the source and calibration metadata for exact settings.

The protected API logs admission and release separately. A `decision` event records each admitted attempt. Before producing any output, the service reserves that admission in a release ledger. A `release` event then records exactly one settlement: `released` (output made available, with the server's output-token count), `failed` (upstream error) or `cancelled` (the client left before anything was emitted). An admission releases at most once, and failed or cancelled attempts still count against the account. Without `HARNESS_STATE_DB`, account horizons, open challenges and the ledger live in process memory, so a restart renews every account. With it, they are kept in a SQLite file that survives restarts. A reservation left unsettled by a crash counts as acquired. A state file belongs to one policy configuration and calibration, and opening it under another is rejected, so use a new file for each arm. The aggregate monitor still lives in memory, so run one worker.

Budget limits restrict what an account can receive over a rolling window, read from the release ledger. Set any of `HARNESS_BUDGET_REQUESTS`, `HARNESS_BUDGET_OUTPUT_TOKENS`, and `HARNESS_BUDGET_CONCURRENCY`; they need `HARNESS_STATE_DB`. `HARNESS_BUDGET_WINDOW_SECONDS` sets the window, seven days by default. Limits are off by default and can be changed on an existing state file. A policy horizon renews attempts and levels but not the budget. A spent account is refused with `budget_exhausted` before embedding or policy state, so these refusals log a decision with `attempt` null and do not count as attempts. Each admission is charged its full output cap until it settles at the server's token count. Failed and cancelled admissions released nothing, so they are not charged, though they still count as attempts. An admission left unsettled by a crash, or released without a token count, keeps its full charge; a crash gives back only its in-flight slot, and the `startup` event reports how many were left open. An optional `X-Idempotency-Key` stops a retry from collecting another answer: reusing a key that released output returns 409, and no answer is stored, so a client that lost a response cannot fetch it again. The limits bound released requests and tokens per account, not what a student learns from them, and more accounts buy more budget. Choose limits from representative traffic and learning curves; no value here is validated.

Each `decision` and `release` event records `policy_revision`, a hash of the policy, calibration and limits. Each decision also records its `reason`: `attempt_cap`, `quota`, `rate`, `detector`, a budget reason, or null.

Calibration uses distinct fitting, score-calibration, and policy-calibration data. Keep a further source-disjoint benign test set and fixed attacker schedules. Synthetic users, shared sources, small account samples, and incomplete windows limit what the resulting rates say about real traffic. A content-based detector may not distinguish an attacker whose request distribution resembles legitimate traffic.

Calibration can record a `mixture_control` that scores shuffled, pooled benign windows against the per-account null. It warns when at least 90% rank below the median account window. The warning identifies a possible blind spot for broad traffic and does not change the adequacy verdict. Older calibrations may not include this control.

The [offline MMD audit](../readings/v4/README.md) reproduced the frozen v3 calibration and logged window scores. Its v2 A1 and A7 ledgers are retained with the audit as evidence for token analysis. In that study, the full policy released all 6,000 A1 responses; broad traffic scored closer to the pooled reference than many specialist benign accounts. Alternative tail tests were exploratory and require independent validation. The audit also identified category bias in the synthetic calibration workload. Correcting it requires fresh workloads and calibration; historical results do not establish current deployment behavior.

## What budgets establish

Budgets and the durable store are access controls, not a detector. They limit what one account can receive. They do not identify an attacker, and they do not change the upper-tail MMD miss described above.

The bound holds for one worker, an intact state file, and a process crash. Under those conditions an account receives no more than the configured requests and output tokens in the rolling window. A state file written before ledger version 2 is rejected, so start a new one. Limits apply to an account label, so several API keys mapped to one label share a budget. Unrelated accounts do not. The in-flight limit is counted per server process, which is why a crash frees its slots.

**Measured.** `uv run pytest tests/test_crash.py` kills the real server process mid-request and restarts it against a stand-in teacher. A one-off run on one Windows host used recorded A1 requests, a 1,215-request budget, and four requests in flight at the crash: 1,211 responses were released and the four open requests stayed charged, totalling exactly 1,215. The in-memory quota released 2,430 across the same crash. An offline replay of the recorded A1 token counts at 1,215 requests a day released 6,000 responses and 588,239 tokens by day five under a daily-renewing quota, against 1,215 responses and 118,024 tokens under a seven-day budget. A 44,200-token budget released 440 responses. These are one campaign, one seed, and one account. They measure enforcement, not capability. On that host the state file added about 2.3 ms at p50 and the budget about 0.3 ms more, with no encoder running, so measure cost on the deployment host.

**Estimated, not measured.** In the [audit's](../readings/v4/analysis/REPORT.md) offline comparison, the six-account A6 campaign stays below a 1,215-request limit and releases all 6,000 responses, while an estimated 44,200-token limit releases 2,706. That token limit reached L4 on 4 of 100 scored benign accounts, against 1 for the request quota, using estimated token costs and synthetic users. No comparison covers a seven-day window, which is stricter than the one-horizon limits the audit fitted.

**Not measured.** No budget has been run with the real teacher, the encoder, or the MMD policy. Student capability under any budget, real legitimate traffic, adaptive attackers, and account rotation are all unknown.

**What this supports.** "Under the stated failure model, the harness bounds the requests and output tokens released to one account in a rolling window."

**What this does not support.** Do not claim that budgets prevent distillation, reduce a student's capability by a stated amount, improve detection, or leave legitimate users unaffected, or that any limit value is safe. A smaller release is not a proportional loss of capability: the audit's development AG News gain came from 500 responses, so a campaign held below 1,215 may still train a useful student. A budget also says nothing about an attacker with more accounts, other data sources, or another provider. Learning curves on fresh sources and a protected run are required before any effectiveness claim.
